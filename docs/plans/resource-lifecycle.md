# 常驻资源生命周期与状态同步

本次调整针对内存评估中的四类问题，按资源归属重整后台工作与 UI 边界，不改变音频功能和外观。

## 1. WebSocket 会话

`SonarEventClient.StartAsync` 和 `DisposeAsync` 共用串行生命周期入口。启动新会话前，取消并等待旧接收任务退出，然后释放旧取消源。令牌在启动任务前取得；最终释放会等待当前会话结束，之后拒绝再次启动。

连接、接收和退避均可取消。旧任务结束前不会启动新接收循环，因此旧会话的断开通知不会落到新会话之后。正常远端关闭也进入退避，避免空转重连。

## 2. 控制消息的接收边界

`SonarMessageReader` 负责接收与组帧，事件客户端负责解析和分发。控制消息累计上限为 1 MiB；第一片未完成后最多允许 10 秒完成组帧。正常空闲等待不受此分片超时限制。

超大消息或未结束的分片会结束当前连接，再由会话重连策略恢复。接收缓冲区归还 ArrayPool，消息缓冲区在所有退出路径释放。该边界针对控制事件流，不限制 HTTP EQ 目录。

## 3. UI 接收当前状态，不保存事件历史

`SonarUpdateInbox` 最多保留六个已知音量通道的最新状态、一条连接状态、一条写入反馈以及一个 ChatMix 刷新标记。部分音量和静音字段独立合并，防止仅有静音的后续事件丢失音量值。

至多安排一个待处理 UI drain；外部事件和本地音量写入确认统一经过该入口。隐藏窗口时只更新有界缓存，显示时一次应用最新状态。释放后丢弃缓存和后续投递。

## 4. 退出与端点切换

`AsyncOperationScope` 管理在途任务：停止接收新工作，取消令牌，等待包括异步收尾在内的任务完成，最后释放取消源。主窗口的状态读取、降级轮询、EQ 加载和命令使用同一窗口级作用域；音量写入器也使用相同规则管理工作任务。

ChatMix 每个端点会话拥有独立的 HTTP 客户端和操作作用域。换端点时先停止并等待旧会话，再释放其客户端、创建新会话；不会直接释放仍被请求使用的客户端。

主窗口退出先停定时器、关闭收件箱并解除后台事件订阅，再异步等待后台接收、音量写入、ChatMix 和窗口在途操作结束，最终释放 HTTP 客户端。UI 线程不再同步阻塞等待这些任务。程序关闭窗口和最终退出均走该流程；普通右上角关闭仍只收起到托盘。托盘菜单也明确释放。

## 验证

- 25 项自动测试，涵盖 300 次并发 StartAsync、重复 Dispose、释放后禁止重启。
- 分片累计恰好到上限、超限、未完成超时、正常空闲和取消接收。
- 5 万次事件及写入确认合并、部分字段保留、未知通道过滤、隐藏窗口不排队、释放后不更新。
- 停止后不接受新任务，等待全部任务与异步 finally，音量工作取消与重复释放。
- 本地延迟 HTTP 服务器下，真实 WPF 窗口连续 10 轮在请求中切换 ChatMix 会话并重复退出；不等待原请求超时，退出后不保留客户端。
- 相同 WPF 弱引用诊断复核：三类绑定模型各 1000 个最终全部回收；45 个关闭窗口未出现逐批累积，最后一个窗口仍可能被框架保留。后续仍需数小时真实使用、休眠唤醒与 GG 重启测试。

短期回收检查不等于长期运行绝无泄漏；不以某一时刻私有内存下降作为修复成功的唯一依据。
